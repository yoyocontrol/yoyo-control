# 账号库：注册账号、用账号绑定设备

2026-11-22 定的方向，**在做**。一个人注册一个账号，他的电脑、手机、浏览器都挂在账号下：新设备登录一次，账号里的电脑就都出现；
移除一部设备，在线的电脑几秒内就不认它。这一整套做成 Yoyo Control 的**库和服务端程序**，任何产品拿去配上自己的登录方式和服务就能用，
不用自己写一行账号代码。产品之间互不相干：每个产品跑自己的账号服务器，账号不互通。

状态的写法和每一步做到哪：见文末「顺序」。

## 不变的规矩

- **电脑只认它自己发的令牌。** 账号服务器签的是**入场券**（短，只给一台电脑）；电脑验过入场券才发自己的令牌，之后每个请求只验它自己的令牌。
- **主人钉在电脑上。** 电脑加入账号时记下账号服务器的地址、签名公钥和主人；之后账号服务器说什么都改不了，换主人只能在电脑上先退出再加入。
- **账号服务器不在数据的路上。** 画面、声音、请求照旧在设备和电脑之间走 uu Link（直连、打洞，不行再经中继），端到端加密（`LINK.md`）。
  它停了，已登录的设备照常用，只是新设备登不进来、撤销发不出去。
- **不登录也能用。** 扫码配对、令牌、Link 和账号无关，一直都在。
- **库里不带任何地址和使用方的名字。** 登录系统、中继、信令、推送……都是运营者在配置里给的。

## 设备锁（每个账号一个开关）

账号服务器能不能直接放人进电脑，是唯一要产品自己选的事。

- **锁关着**：入场券就够。设备登录 → 账号服务器签券 → 电脑认。方便；代价是运营账号服务器的人（或攻破它、盗了登录账号的人）能进账号里的每台电脑。
- **锁开着**：电脑还要看到一台**已信任设备**的签名为这部新设备背书。已信任的设备各有一把锁钥匙（Ed25519，在设备上生成、不出设备）；
  新设备登录后，已信任的设备上弹出「允许“B”吗？」，点允许 = 用锁钥匙签 `{ account, device, key }`。电脑同时核对入场券和背书。
  攻破账号服务器、盗了登录账号，都只拿得到入场券。和 Tailscale 的 Tailnet Lock 一个思路。

细节：

- 锁钥匙的集合是一条**签名链**：第一条（开锁）由开锁的设备签，之后每次加 / 减锁钥匙都要集合里现有的一把签。电脑加入时钉住链头，之后跟着撤销名单
  一起取新的条目，逐条验签。账号服务器只能转交，造不出、删不掉。
- 开锁时生成几个**关锁密钥**（只显示一次，链里只存哈希）：所有已信任的设备都丢了，用它关锁。另一条退路一直在：走到电脑前扫码配对。
- 锁关着时电脑也接受一条新的开锁链（那只会让它更严）；锁开着时，关锁要关锁密钥，账号服务器单独做不到。
- 默认开还是关由运营者在配置里定（`lock: "on" | "off"`），用户可以改。

## 组成

| 包 | 在哪跑 | 做什么 |
| --- | --- | --- |
| `@yoyocontrol/account-server`（`packages/account-server`） | 运营者的服务器 | 账号服务器本身：登录、目录、入场券、撤销名单、设备锁的链、服务、订阅、管理命令 |
| `@yoyocontrol/account`（`packages/account`） | 电脑（Node：Linux、Windows 服务端，及任何 Node 写的服务）；借出服务的那一端 | 电脑这一半（`AccountMember`）：加入 / 退出、钉主人、验入场券和背书、跟撤销名单、取服务；服务验服务票（`ServiceKeys`） |
| `YoyoServer` 里的 `AccountMembership` | 电脑（Mac） | 同上，Swift |
| YoyoKit 的 `YoyoAccount` | iPhone / iPad | 登录、电脑清单、拿入场券、扫码添加电脑、锁钥匙和批准 |
| `@yoyocontrol/account-web`（`packages/account-web`） | 浏览器 | 网页的登录（会话绑在不可导出的设备钥匙上，每个请求签名）、清单、入场券 |

电脑这一半给服务端的只是一个判断：「这个 hello 带的入场券（和背书）放不放行，放行的是账号里的哪部设备」，以及撤销名单变了时「哪些令牌作废」。
令牌怎么发、存在哪仍是服务端自己的事（Mac / Linux 的 `devices.json`，或使用方自己的登录模块）。

## 账号服务器

一个 SQLite 文件（`node:sqlite`）加签名钥匙文件，都 0600。可以作为程序跑（`yoyo-account-server`，配置是环境变量，全部列在
`packages/account-server/src/main.ts` 开头；管理命令 `yoyo-account-admin`），也可以作为库挂进运营者自己的 HTTP 服务
（自己建 `AccountConfig`，`new AccountService({ cfg, store, ring, idp }).handle` 是 Node 的请求处理函数）。

**登录**（`providers`，可以同时开几种）：

- `oidc`：任意 OpenID Connect（自己的、Keycloak、Google、微软……）：发现文档、授权码 + PKCE、nonce。账号 = `iss` + `sub`。
  谁都能注册的登录系统必须给 `allow`（`sub` 或 `@域名`）或明说 `open`。
- `apple`：iOS 上的原生「通过 Apple 登录」（`ASAuthorization` 给的 identityToken 直接交给服务器验：Apple 的公钥、`aud` 在运营者给的 bundle id 里、nonce）。
  Apple 也是 OIDC 提供方，网页走 `oidc` 那条。删除账号时撤销 Apple 授权（运营者给 Sign in with Apple 的钥匙才做）。
- 设备拿到的会话：令牌只存 SHA-256；App 最长 90 天，网页 30 天且绑在设备钥匙上。

**电脑加入**（都由那台电脑自己的 Link 钥匙签名证明它是谁）：

- 加入码：电脑要一个码，显示二维码；已登录的设备扫码同意；电脑再确认一次是谁同意的（名字和登录系统里的编号），坐在电脑前的人说「是」才算。
- 事先说好是谁（`expect`）：没有屏幕的电脑声明期望的账号，对的账号同意后自动确认。
- 加入钥匙：管理员给某个账号造的一次性钥匙，电脑凭它直接加入。
- 经已配对的设备：已经和电脑配对过的设备（经 Link，已有电脑自己的令牌）让电脑签一份「我加入账号 X」，交给账号服务器。用户登录后，App 把本机
  配对过的电脑逐台这样加进来，什么都不用点。

**入场券**：`POST /v1/tickets { computer }` → EdDSA 签名的 JWT：`iss`、`sub`（账号）、`aud`（电脑的 Link id）、`dev`（设备 id、名字、公钥摘要）、
`sx`（设备在账号服务器的登录何时到期）、`jti`，120 秒。电脑发的令牌从不超过 `sx`。凭入场券进来的设备不能再替别人出配对码。

**撤销名单**：每个账号一份，带版本号，整份签名：被移除的设备、被移出的电脑、账号是否停用，加上设备锁的新条目。电脑用 Link 钥匙签名去取
（长轮询，没变就挂着等）；版本号不低于时钟，库从备份恢复也不会倒退。电脑看到签了名的名单里有自己，就退出账号（服务器只是「不再列出它」不算）。

**服务**（可选）：运营者给账号里的电脑带去的东西，库不认识它们是什么（`AccountConfig.services`，按名字）：

```
{ name: "relay", kind: "fixed", value: () => ({ url, token }) }   // 每台电脑一样，原样交出；null = 这会儿没有
{ name: "push",  kind: "token", url, service: "push" }            // 每台电脑一张自己的服务票（aud = <ns>-push，一天），服务用账号服务器的公钥验
```

环境变量给的是常用的几样：`relay`（`ACCOUNT_RELAY_URL` + 令牌）、`push`、`speech`、`signal`（只跟 relay 一起、不能等于 relay 的令牌）、
`web`（`ACCOUNT_WEB_REDIRECTS` 第一个的 origin）。回答是 `{ <名字>: {…} | null }`，没配的名字不出现。电脑用 Link 钥匙签名去取（启动时、
之后每 6 小时、自己的票快到期时），`AccountMember.services()` 按名字给出；电脑端的 `validServices` 只留完整的条目，使用方自己的规则
（这个要跟着那个）用 `options.validServices` 加。

**订阅**（可选，`entitlements`）：`appstore`：验 StoreKit 的交易 JWS（证书链到 Apple Root CA - G3、bundle id 和产品 id 由运营者给），一份订阅归最后上报的账号。
结果放在账号的 `entitlements` 里给设备和运营者自己的服务看。以后加别的来源（网页支付）也是同一个位置。

**签名钥匙**：Ed25519，第一次启动时生成；轮换时新钥匙由上一把背书，电脑只接受能从它钉住的公钥一路背书过来的。

**管理命令**：列账号、预先建账号、加入钥匙、停用 / 恢复 / 删除、撤销设备、换登录系统的 `iss`、轮换钥匙。

## 格式和已有的部署

- 报文和存储沿用库的来源——当时最完整的那份实现，库表结构一样（`SCHEMA_VERSION` 不变）。
- 线上的名字都由一个**命名空间**拼出来（`Wire`；账号服务器 `ACCOUNT_NAMESPACE`，电脑 `AccountMember` 的 `namespace`，服务 `ServiceKeys` 的
  `wire`），默认 `yoyo`：`<ns>-ticket+jwt`、`<ns>-revocations+jwt`、`<ns>-service+jwt`、`<ns>-key-endorsement+jwt`（钥匙里的
  `<ns>_endorsement`）、签名的文本 `<ns>-account-computer-v1` 等、会话 `<ns>_as_…`、加入钥匙 `<ns>_jk_…`、电脑的请求
  `Authorization: <Ns>Link …`、网页的 `<ns>-proof`、服务 `<ns>-<名字>`。已经在跑的部署把命名空间设成它原来用的那个，库、钥匙、电脑上的
  成员文件都原样接着用，已加入的电脑不用重新加入。
- 账号服务器的 `ACCOUNT_APP_REDIRECTS` 没有缺省值（以前的实现缺省是它自己 App 的地址）：要 App 登录就写上。

## 顺序

1. **账号服务器和 Node 的电脑端进库**：`packages/account-server`、`packages/account`（0.1.0，还没按 `git-dist.sh` 发布），以现有最完整的实现为底子，
   去掉具体产品的名字，测试跟着进来，另加电脑端对着真服务器的测试（`account-server/test/member.test.ts`）。（有，2026-11-22）
2. **第一个使用方换成用库**：行为不变，证明库能直接用；之后那边不再有自己的账号代码。（没做）
3. **Yoyo Control 自己换过来**：signal1 用 `account-server`（Apple 登录、Pro 订阅、锁默认开），Mac 的 `AccountMembership`、Linux / Windows 用 `@yoyocontrol/account`，
   iOS 用 `YoyoAccount`；现有账号按 Apple 的 `sub` 保留，电脑由已配对的 iPhone 自动重新加入；现在的「定向码」批准换成设备锁的背书。（没做）
4. **设备锁**：链、背书、关锁密钥，账号服务器、电脑端、iOS、网页一起。（没做）
5. **`account-web`**：网页的登录和清单。（没做）

每一步做完在这里改状态；发布 npm 包按 `scripts/git-dist.sh`，Swift 按 `kit-vX.Y.Z`。
